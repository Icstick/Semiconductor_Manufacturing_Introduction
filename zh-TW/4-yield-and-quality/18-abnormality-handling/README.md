## 異常一定會發生

晶圓廠裡有上千台機台、數百個步驟，異常一定會發生：數據超出管制界限、機台發出警報、缺陷數突然增加、作業出錯。

要把這件事講清楚，得先承認一個前提：**這不是一個「會不會出錯」的問題，是一個「什麼時候、以什麼形式出錯」的問題。**

一台機台有幾千個零件，一個步驟有幾十個參數，一座廠有上千台機台。只要其中任何一個地方有一點偏差，就有機會變成一顆壞晶粒。用機率算，出錯不是意外，是統計上的必然。

所以重點不是「永遠不出錯」，而是**出錯時能快速、一致地處理**，把損失降到最低。

異常的種類大致可以這樣分：

| 類型 | 例子 | 特徵 |
|---|---|---|
| 數值異常 | 量測值超出管制界限 | 有明確的訊號與時間點 |
| 機台異常 | 警報、停機、感測器讀值異常 | 通常先於產品異常出現 |
| 缺陷異常 | 缺陷數突然跳高、出現新的缺陷型態 | 需要複檢才知道嚴重程度 |
| 人為異常 | 用錯 Recipe、放錯批次、漏做步驟 | 不一定有訊號，靠紀錄發現 |
| 環境異常 | 停電、斷水、潔淨度失控 | 影響範圍大，通常全廠級 |

處理異常的基本順序如下：

**發現異常 → 擋住影響 → 找出範圍 → 判定處置 → 找出根本原因 → 防止再發**

這六步的順序不是隨便排的。它反映了一個很務實的優先順序：**先止血，再診斷。**

## OCAP：事先寫好的應變步驟

異常可能發生在半夜，當班的人不一定是最熟悉這個製程的工程師。所以工廠會為每一種常見的異常，事先寫好處理步驟。

這套東西的重點不是「寫得漂亮」，是「半夜三點有人照著做也不會做錯」。

> [!NOTE]
> **📖 名詞｜OCAP（Out of Control Action Plan，異常處理計畫）**
>
> - **定義**：針對特定異常，事先規定好「要檢查什麼、要做什麼、要通知誰」的處理步驟。
> - **現場用法**：「這個 OOC 照 OCAP 走，先停機台、量控片。」
> - **相關名詞**：OOC、Hold、SPC
> - **常見混淆**：OCAP 不是事後的檢討報告，而是異常發生「當下」的行動指引。它讓不同班別、不同的人都用同樣的方式處理。

一份好的 OCAP 通常包含這幾件事：

- **這個異常長什麼樣**：哪一張圖、哪一個參數、什麼樣的變化。
- **第一步做什麼**：通常是停機或擋片，而不是先查原因。
- **要量什麼來確認**：控片、重測、交叉比對。
- **什麼情況下可以恢復**：明確的判準，不是「感覺可以了」。
- **要找誰**：值班工程師、製程負責人、設備工程師的聯絡方式。

最後一項常常被寫得很隨便，但它其實最關鍵。半夜三點，一個不知道要找誰的人，會做出兩種事：一種是硬著頭皮自己決定，另一種是把機台停著等到早上。前者可能擴大損失，後者可能損失一整夜的產能。

## Hold：先擋下來

發現異常後，第一個動作通常是 **Hold**：把可能受影響的晶圓擋下來，暫停生產；有問題的機台也會被停用，不讓更多晶圓進去。

Hold 有幾個特點：

- 每一個 Hold 都要記錄原因和負責人。
- 只有被授權的人才能解除 Hold。
- 也可以設定**預約 Hold**（Future Hold）：讓晶圓先繼續生產，等走到指定的步驟時再自動擋下，例如等下一站的量測結果出來再判斷。

這三個特點，其實對應三個不同的風險：

| 特點 | 防的是什麼風險 |
|---|---|
| 記錄原因與負責人 | 沒人記得為什麼擋，最後被隨便解除 |
| 只有授權的人能解除 | 趕出貨時有人偷偷放行 |
| 預約 Hold | 擋得太早浪費產能，擋得太晚已經做完 |

預約 Hold 是這三者裡最巧妙的設計。它承認了一件事：**不是所有異常都值得立刻停線。**

如果某一站的量測結果要等到下一站才出來，那麼現在就把整批擋下來，只是讓晶圓在倉庫裡等。更好的做法是讓它繼續走，但在下一個關鍵步驟之前自動停住——這樣既不會漏掉，也不會白白浪費時間。

> [!TIP]
> **🔧 Know-how｜第一件事是擋住，不是修好**
>
> - **情境**：發現某台機台的結果異常。
> - **做法**：先停機台、Hold 可疑的晶圓，再開始調查原因。
> - **為什麼**：調查原因可能要花好幾個小時。如果邊查邊讓機台繼續生產，受影響的晶圓會越來越多。
> - **沒做會怎樣**：原本只影響一兩批的問題，擴大成十幾批甚至更多，損失成倍增加。
> - **相關章節**：[第 17 章 製程控制](../17-process-control/README.md)

Hold 也有成本，而且是很多人不會去算的那一種：**晶圓停在廠裡，就是在燒錢。**

一片晶圓的先進製程成本以千美元計，一批二十幾片就是幾萬美元起跳。這些錢在晶圓被 Hold 住的時候不會消失，只是變成「在製品」壓在帳上。Hold 得越久，週轉越慢，同樣的產能在同樣的時間裡產出越少。

所以 Hold 的決策其實是一個天平：**多擋一片，是浪費；少擋一片，是風險。** 這條線怎麼劃，就是下面幾節要處理的事。

## 找出影響範圍

擋住之後，要確定**哪些晶圓可能受到影響**。這時工廠系統記錄的履歷就派上用場：查出在異常期間，有哪些晶圓經過這台機台、這個腔體。

> [!TIP]
> **🔧 Know-how｜影響範圍從「上一次確認正常」開始算**
>
> - **情境**：機台在今天下午被發現異常，但不知道是從什麼時候開始的。
> - **做法**：往回找到這台機台最後一次確認正常的時間點，例如上一次控片量測合格的時間。從那之後經過這台機台的所有晶圓，都列入可疑範圍。
> - **為什麼**：異常可能早在被發現之前就開始了。只擋發現當下的晶圓，會漏掉更早受影響的晶圓。
> - **沒做會怎樣**：有問題的晶圓被放行，到測試甚至客戶端才發現。這也是機台需要定期檢查的原因：檢查越頻繁，可疑的範圍就越小。
> - **相關章節**：[第 23 章 工廠如何被系統管理](../../6-beyond-the-fab/23-fab-systems/README.md)

這條規則值得拆開來看，因為它同時解釋了兩件事。

第一，**「發現異常的時間」和「異常開始的時間」是兩個不同的時間。** 中間那一段，就是風險所在。找出這段區間的長度，靠的是「上一次確認正常」的紀錄——所以工廠會定期用控制片（monitor wafer）去驗證機台，本質上是在替這段區間畫一個上限。

第二，**檢查的頻率決定了風險的上限。** 一天檢查一次，最壞的情況是二十幾個小時的產出全部可疑；一小時檢查一次，最壞只是一小時。但檢查本身也要花時間與機台，所以這又是一個取捨。

找出範圍之後，還要決定「範圍內怎麼處理」。這時候通常會分層：

- **確定受影響**：有直接證據，例如在同一時段、同一腔體、同一批。
- **可能受影響**：時間或設備有重疊，但沒有直接證據。
- **確定不受影響**：時間、機台、產品都對不上。

只有第二層需要傷腦筋，因為它要靠後續的量測或測試來判定。

## 判定：放行、重工或報廢

確定範圍後，要決定每一批晶圓的命運：

| 處置 | 意思 | 適用情況 |
|---|---|---|
| 放行（Release） | 確認沒有影響，繼續生產 | 異常不影響產品品質 |
| 重工（Rework） | 去除部分結果，重新做一次 | 可以重做的步驟，主要是微影 |
| 報廢（Scrap） | 晶圓不再繼續生產 | 損壞無法挽回，或繼續做的風險太高 |
| 有條件放行 | 繼續生產，但加強後續檢查或特別標記 | 影響還不確定，需要更多數據 |
| 降級（Downgrade） | 降低規格出售 | 功能可用，但速度或功耗不達標 |

影響較大或不確定的情況，會召開**物料審查會議**（Material Review Board，MRB），由製程、整合、品保等部門共同決定，必要時也會通知客戶。

MRB 的存在，是因為這一類決定不能只由一個人做。

製程工程師會傾向「再給它一次機會」，業務會傾向「先出貨再說」，品保會傾向「全部報廢」。三個人都對，但三個人的風險偏好不一樣。MRB 的價值不是投票，是**把三個人的理由攤在同一張桌上**，讓決定留下紀錄。

決定處置之後，還要找出**根本原因**、執行改善對策，並確認同樣的問題不會再發生。

## 一次異常要花多少錢

異常處理的每一步都有價格，把它們列出來，會發現決策的邏輯其實很簡單。

| 成本項目 | 內容 | 量級 |
|---|---|---|
| 在製品積壓 | 被 Hold 的晶圓占用的資金與產能 | 一批數萬美元，先進製程更高 |
| 重工 | 去除、重做、再量測 | 每片數十美元，加上機台時間 |
| 報廢 | 整批晶圓與已投入的製程成本 | 一批數萬到十萬美元級 |
| 產能損失 | 機台停機期間少做的片數 | 一天以百萬美元計的產值規模 |
| 客訴與召回 | 不良品流到客戶端之後的處理 | 遠高於前四項，且傷商譽 |
| 調查成本 | 工程師時間、FA、實驗批 | 四位數美元起，視複雜度 |

這張表最重要的訊息，是**第五項的量級和其他所有項都不一樣**。

一批晶圓報廢，損失的是幾萬美元；一批不良品流到客戶端，可能是整批退貨、產線停擺、合約罰款，甚至失去客戶。所以異常處理的預設方向永遠是「寧可多擋」，而不是「先出貨看看」。

但「寧可多擋」也有代價。擋得太多，好片被誤殺，良率白白損失；擋得太久，週轉變慢，產能下降。真正成熟的工廠，是在這兩個方向之間找一個**有紀錄、可檢討**的位置，而不是靠某個人的直覺。

這也是為什麼每一次處置都要留下理由：不是為了應付稽核，是為了下次遇到類似情況時，有一個可以參考的先例。

## 根本原因：從現象到機制

擋住、判定、恢復生產，事情只做了一半。真正讓問題不再發生的，是找到**根本原因**。

但「根本原因」這四個字經常被誤用。它指的通常不是「最後那個原因」，而是「拿掉它，問題就不會再發生的那一層」。

同一個異常，可以往下追好幾層：

| 層次 | 例子 | 拿掉它會怎樣 |
|---|---|---|
| 現象 | 這批晶圓的線寬偏大 | 只是描述，什麼都沒改變 |
| 直接原因 | 曝光能量設定錯了 | 這批修正，下一批可能再犯 |
| 根本原因 | 換料後沒有人重新驗證參數 | 補上流程，類似問題不再發生 |
| 系統原因 | 換料與參數驗證沒有綁在一起 | 改了制度，其他步驟也受益 |

實務上最常見的錯誤，是停在第二層就收工——**把「這次的原因」當成「根本原因」。**

常見的追問方式是連問幾次「為什麼」，一層一層往下。這個方法很土，但它有效的原因很簡單：它強迫你從「誰做錯了」轉向「什麼讓這件事變得可能」。

這也是為什麼「加強教育訓練」通常不是一個好答案。它假設問題出在人，但人本來就會犯錯；一個需要人記住才不會出錯的流程，遲早會出錯。

比較好的對策是**防呆**：讓錯誤根本不可能發生，或至少在下一個步驟就被擋住。

- 用錯 Recipe 裝不上去，而不是靠人核對。
- 兩片晶圓不會同時進同一個腔體，而不是靠人記得。
- 參數沒驗證就無法放行，而不是靠人簽名。

找到原因之後，還要驗證對策真的有效——不是「應該有效」，是「用數據證明有效」。做法通常是回到同一台機台、同一組條件，確認原本的異常不再出現。

防呆的成本通常比事後補救低，但它的設計需要在事前想清楚，而那正是最容易被跳過的一步。

## 工程變更：改變也是一種風險

不只異常需要管理，「改變」本身也是風險。修改 Recipe、調整流程、更換材料或供應商、新增機台，都可能影響產品的電性、良率和可靠度。

所以任何變更都要經過正式的流程：評估風險、用實驗批驗證、必要時做可靠度測試，通過審核才能正式上線。重大的變更還必須事先通知客戶。

變更的風險不是均勻的，所以實務上會分級：

| 變更類型 | 例子 | 通常要多嚴格 |
|---|---|---|
| 同類型替換 | 同規格、同供應商的材料 | 文件審核，必要時小批驗證 |
| 參數微調 | 溫度調整一兩度 | 實驗批驗證，確認電性與可靠度 |
| 流程變更 | 增加或刪除一個清洗步驟 | 完整驗證，含可靠度測試 |
| 新機台或新廠 | 導入新生產線 | 全產品驗證，客戶通知 |
| 設計變更 | 改光罩、改電路 | 重新設計驗證，通常另有一套流程 |

分級的意義，是把驗證的力氣花在風險高的地方。全部都用最嚴格的流程，會慢到無法運作；全部都用最寬鬆的流程，早晚會出事。

一次變更要走的關卡，大致是這幾步：

- **提出與說明**：改什麼、為什麼改、預期效果。
- **風險評估**：可能影響哪些產品、哪些參數、哪些可靠度項目。
- **實驗批驗證**：用分批實驗確認效果，同時確認沒有副作用。
- **可靠度驗證**：必要時做加速壽命測試，確認長期不會出問題。
- **上線與監控**：小批量先行，確認量產數據與實驗一致才全面推行。
- **客戶通知**：影響到產品規格或可靠度時，發出 PCN。

這六步裡，最常被省略的是「上線與監控」。實驗批的條件通常比量產乾淨，所以實驗做出來的結果往往比量產好一點；如果不做小批量先行，這個差距就會在全面推行之後才浮出來。

> [!NOTE]
> **📖 名詞｜ECN 與 PCN（Engineering Change Notice / Process Change Notification）**
>
> - **定義**：ECN 是工廠內部的工程變更通知與審核流程；PCN 是對客戶發出的製程或產品變更通知。
> - **現場用法**：「這個 Recipe 改動要走 ECN」「換材料要發 PCN 給客戶」。
> - **相關名詞**：變更管理、驗證、可靠度測試、分批實驗
> - **常見混淆**：不是只有大改動才要走流程。看起來很小的修改，例如調整一個溫度參數，也可能影響可靠度，所以同樣要經過評估。

變更管理最難的地方，不是寫文件，是**抵抗「這次應該沒差吧」的誘惑。**

一個參數調一兩度，聽起來確實沒差。但晶圓廠的教訓幾乎都來自這一類「應該沒差」：某個材料換了供應商、某個步驟的順序調了一下、某台機台的零件換成另一家——單看都合理，疊起來就是一個沒人預期的失效。

所以流程的本質不是懷疑人，是承認**人無法預測複雜系統的連鎖反應**。

## 常見異常

| 異常 | 可能原因 | 結果 |
|---|---|---|
| 半夜 OOC，無人處理 | OCAP 沒寫清楚、通知鏈斷掉 | 異常持續到早班才被發現 |
| Hold 被提早解除 | 趕出貨、權限管理鬆散 | 有問題的晶圓流出 |
| 影響範圍估得太小 | 只看發現時間，沒回推上次正常 | 更早的受影響批被放行 |
| 同一異常反覆發生 | 只修了直接原因，沒找根本原因 | 每次都要重新處理一次 |
| 重工次數過多 | 沒有上限、或每次都僥倖過關 | 底層材料被損傷 |
| 變更沒走流程 | 覺得「只是小改」 | 事後才發現可靠度出問題 |
| 客訴後才發現廠內早有警訊 | 警報被忽略、數據沒人看 | 損失擴大到客戶端 |
| 處置決定沒有紀錄 | 口頭決定、事後說不清 | 同樣的爭論每次重來 |

## 本章重點

1. 異常一定會發生，重點是快速、一致地處理；順序是擋住影響、找出範圍、判定處置、找出根本原因、防止再發，先止血再診斷。
2. OCAP 讓不同班別的人都用同樣的步驟處理異常；影響範圍要從上一次確認正常的時間點開始算，檢查頻率決定風險的上限。
3. 任何工程變更都要經過評估與驗證，重大變更還要通知客戶；變更分級是把力氣花在風險高的地方。
4. 根本原因不是「這次的原因」，而是拿掉它問題就不再發生的那一層；最好的對策是防呆。
